# 通販の配送通知：確認待ち取込と自動反映の残件

アプリに本人限定の配送通知確認を接続する実装。現在は未確認通知の台帳取込だけを行い、買い物商品や在庫は変更しない。実メールによる自動受取完了は未稼働。

`lib/commerce-model.ts` の `applyCommerceEvents(items, ledger, events)` は、更新後の商品、接続別の台帳、確認事項、今回完了した商品IDを返す。ShoppingState v4の形式は変更しない。呼び出し側が商品状態と台帳を一緒に原子的に保存する必要がある。

- 注文確認にある接続先・注文行・商品キー・数量・単位・注文日時がすべて確定し、注文前に作った未購入候補が1件だけの場合に対応付ける。商品名では推測しない。
- 配達通知は対応付けた注文行と配送IDを参照する。配送ごとの明示数量が注文数に達した場合だけ、`status: received` と日常リストへの移動を反映する。配達予定日や文章の雰囲気では完了にしない。
- 在庫、購入数量、在庫確認状態、購入日、配送予定日、添付、メモは変更しない。実際の配達数・配達日は別台帳に残す。
- 部分配達・重複通知・通知順序の逆転を扱う。複数注文との競合、数量不明、取消・返品、商品や在庫の手動変更は確認待ちにする。
- docomo収集側の初版は実メール未検証のため、`explicitConfirmed: false` を返す。この通知では自動で購入完了にせず、確認事項だけを作る。

`scripts/commerce-model.test.ts` は合成データだけを使う。本番のメール・買い物データ・認証情報はテストや公開ソースへ含めない。

## 確認待ち取込の構成

- 設定の「配送通知」で取込件数・確認待ち・最後のメール取得時刻・未取得範囲を表示。アプリの確認時刻とメール収集時刻を区別する。
- GET `/api/commerce` は本人用の保存済み状態だけを読む。POST `/api/commerce/sync` は保存済みrevisionのみ受け取り、固定Workerから100件以内を読み込む。別アカウント・ブラウザ指定の接続先や通知・所有者は受け付けない。
- サーバー設定名は `DOCOMO_EVENTS_URL`、`DOCOMO_EVENT_READ_TOKEN`、`DOCOMO_INTEGRATION_ID`、`DOCOMO_OWNER_HASH`。すべてSitesの秘密設定に保存し、値をソースへ入れない。
- `shopping_commerce_connections` に確認台帳・カーソル・取得状態をまとめて保存。現在の買い物revisionと連携revisionへのCAS、操作IDで並行取込や他端末の編集を確認する。買い物snapshot自体は書き換えず、既存の設定・料理履歴・未知フィールドも保持する。
- 現APIは `explicitConfirmed:false` だけを受け入れ、trueを主張する通知を拒否する。将来の自動適用には送信元の信頼根拠、商品行と配送の対応、数量、明示配達完了、在庫計上方針、検証済み派生イベントとsnapshotの原子的保存が必要。
- 定期収集・自動完了・通販お気に入りの継続取得は、この確認画面の完成とは別に扱う。
